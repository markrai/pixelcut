# Desktop prototype (Phase 1A / 1B)

## Project contract

The project format is versioned JSON with asset references, tracks, clips, integer microsecond timestamps and optional display-oriented crop rectangles. Source in/out intervals are half-open. Timeline placement is independent of source time. Clips may not overlap within a track; different tracks can overlap in the model. Splitting preserves the source interval and does not mutate the input project. Save As writes a new project file and refuses overwrite; absolute paths are stored. Source files are not copied or changed.

The model accepts multiple tracks, but the initial desktop shell supports one V1 track with an empty A1 placeholder. Audio remains attached to its video. Import currently accepts the validated HLG video profile; unsupported audio or auxiliary stream combinations may still fail at export. Missing or moved source files are reported when accessed.

## Native rendering feasibility

The first Windows prototype uses Win32 controls and an external mpv process embedded into a child HWND using mpv's documented --wid option. It keeps gpu-next, software decode and the same SDR target configuration as the qualified CLI preview. This avoids introducing Qt bindings, a C++ build toolchain or a browser color conversion path before the embedding experiment passes. Qt/libmpv remain possible production choices; the process boundary is not a commitment to the final GUI.

Preview plays a selected source interval rather than a composited timeline. Committed crop is visualized using the shared FFmpeg-compatible filter plan; other transforms and timeline composition are not yet supported. Export dispatches a selected clip to the existing audiovisual remux or HDR render path. No project-wide exporter is provided yet. Do not equate native embedded SDR preview with native HDR output qualification.

## Windows acceptance procedure

1. Build and launch the desktop executable from a command prompt. Import an original Pixel HLG recording. The media bin should show its displayed portrait dimensions.
2. Add it to V1. Select the clip and play it; verify video renders inside the preview pane, audio works, and appearance agrees with the existing CLI preview. Stop and repeat playback, including several different source intervals. Verify closing the application terminates its player.
3. Set source in to 2 seconds, source out to 7 seconds, and crop to 40,40,1000,1840 for a displayed 1080 x 1920 source. Apply, export to a new MP4 and inspect it with the CLI. Expect five seconds, 1000 x 1840, 10-bit HLG and no rotation requirement.
4. Split the clip at a timeline position strictly inside it; verify that the resulting intervals meet without overlap. Undo and redo. Save as a new project, reopen and verify the edits survive.
5. Verify invalid intervals, overlaps, odd crop coordinates, missing media and existing output files fail without altering sources. Verify the desktop stays responsive during import/export.
6. Compare export playback against the original and existing CLI export in VLC and mpv. Record Windows Media Player discrepancies separately. Confirm embedded preview does not degrade appearance.

The project model can be tested automatically; cross-compilation and a Windows build are not evidence of successful native playback. Physical Windows display, embedded player lifecycle, layout/DPI, and user interaction are explicit acceptance gates.

## Graphical timeline and desktop styling

The Windows shell uses a dark native GDI palette, owner-drawn buttons, Segoe UI, a resizable window and a double-buffered timeline. The video lane is editable; the audio lane is a representation of linked source audio, not an independent track. Clip body drag changes placement, edge drag changes source in/out and left edge placement. Changes are committed only on mouse release after project validation, with invalid overlap rejected. The model tests cover clamping, movement and overlap rejection. Undo restores committed edits. A ruler click sets the playhead and split time; Play clip starts at that point when inside the selected clip. During playback the playhead follows mpv's observed time-pos through a per-session Windows named pipe. Ruler scrubbing seeks within or across clips; sequential cross-clip playback is not yet implemented. Zoom and horizontal scroll affect view state only.

Acceptance: resize the window, import a clip, drag it, trim both edges, split at a clicked ruler position, undo, zoom and scroll, and confirm source preview and export remain consistent. Verify at the display's actual DPI. The media encoding path is unchanged.

## Keyboard and cursor acceptance

Check both timeline and embedded preview focus, natural end-of-file, repeated play/stop, and focus after playback ends.
- Ctrl+N/O/S/I/E invoke new/open/save-as/import/export. Ctrl+Z, Ctrl+Y and Ctrl+Shift+Z invoke undo/redo. Ctrl+K or S splits the selected clip at the timeline playhead; Delete removes it. F fits the timeline; plus/minus zoom. Left/Right moves the marker by 100 ms; Home/End moves to the project boundaries. These commands seek the preview but are not frame stepping.
- Tab and Shift+Tab navigate the editor controls; Enter applies numeric properties while focused in a property field. Native text selection, deletion and undo are preserved. F1 opens the shortcut reference. No global keyboard hook is installed; mpv focus supports pause keys but not all editor commands.
- Hover over a video clip body, left edge, right edge, ruler and empty timeline. Confirm four-way move, horizontal resize, crosshair and normal arrow cursors respectively. Invalid overlapping drags show a prohibited cursor. Linked audio shows a selection hand only where audio exists. Clip hit testing is shared by cursor selection and drag initiation.
- Check that holding Space or Delete does not repeatedly trigger actions, Escape cancels an uncommitted drag, and shortcut commands do not execute while an import/export is active. Verify the source and HDR export path are unchanged.

## Playback-synchronized playhead

The editor polls mpv's JSON IPC time-pos, seeking, pause and eof-reached properties through a unique Windows named pipe for each preview. The UI samples the latest reported position every 33 ms; no wall-clock estimate is used. Source timestamps are clamped to the clip's source interval and translated into project time by adding the timeline start and subtracting the source in point. The accent playhead crosses both lanes, the timestamp display shows milliseconds, and the timeline scrolls to keep the playhead visible. The eof-reached property moves the marker to the clip end. Manual pause retains the decoded frame; Space resumes. Ruler clicks and scrubs send absolute exact seeks mapped to source coordinates. No automatic next-clip transition or frame-accurate seeking guarantee is provided yet.

Acceptance: play an untrimmed clip, watch the playhead advance, stop with Space, verify the marker freezes, play again, and confirm playback resumes at the marker. Repeat with a trimmed clip placed at a nonzero timeline start. Zoom until the playhead reaches the edge and verify the view follows it. Let playback reach the end and test Space/Esc with focus on the embedded player. Windows CI covers bidirectional timestamp conversion and seek-request coalescing; native pipe connection, timing, scrolling and focus require physical Windows testing.

## Bidirectional preview seeking

The preview stays loaded when paused. The same IPC worker issues seek and pause commands and polls player state; mpv's own on-screen controller and default key bindings are disabled to avoid seeking outside the editor's clip boundaries; UI events publish only the latest desired seek rather than blocking on the pipe. Ruler scrubbing temporarily pauses and resumes the prior playback state on release. Click a clip or use arrow/Home/End shortcuts to seek. When crossing clip boundaries manually the player is replaced; a gap clears the preview. Clip end is fixed to the source out-point, independent of the initial seek location. Test forward/backward seeks while playing, paused and after EOF, rapid scrubbing, trimmed/moved clips, cross-clip jumps, gaps and repeated Space presses. Exact seek may be slower for long-GOP files; crop is visualized through the separate visual crop workflow. Physical Windows IPC responsiveness and displayed-frame accuracy remain qualification items.

## Phase 2B.2a: Visual cropping

The embedded mpv process loads a bundled Lua script from a temporary file. The script draws a shaded full-source crop rectangle, thirds guides and eight handles using mpv's own OSD coordinates. The crop session pauses playback, keeps a draft separate from the project and uses even, display-relative pixels. Shift held at drag start locks the initial ratio approximately, subject to pixel rounding and source bounds. Apply commits one undoable project change, Cancel leaves the project unchanged, and Reset removes the crop. A committed rectangle is translated to the encoded orientation using mpv's rotation property and applied through the shared geometry filter plan; no preview transcode or export pipeline change is needed. The source recording is never modified. Position/scale on a project canvas, rotation and flip are deferred until their preview and export contracts are implemented.

Windows acceptance: import test.mp4, seek to a recognizable frame, enter Visual crop, drag each handle, drag the interior, try Shift-drag, apply and verify the resulting composition. Compare an asymmetric crop on portrait and landscape footage against CLI export, not merely dimensions. Test cancel, reset, undo/redo, reopening a project with crop, resizing the editor and playback after apply. Confirm the source rectangle remains within bounds and even-aligned. Test the visual crop with mpv 0.42 on TITAN; actual overlay interaction and orientation equivalence remain unqualified until this passes.

## Phase 2B.2b: Position and scale

Optional per-clip transform fields extend version 1 projects without changing existing clip behavior. Canvas dimensions are explicit even pixel sizes. Uniform scale is relative to the fitted cropped source, and X/Y offsets are relative to the centered scaled image. The planner calculates even-aligned visible intersections and rejects fully off-canvas images and excessive allocations. Crop precedes scale, clipping and black padding, with square-pixel output. The same filter plan is used by FFmpeg export and mpv lavfi preview; the preview explicitly normalizes cardinal source rotation and clears rotation on the filtered output. Only limited-range HLG is supported for transforms until full-range padding is qualified. A numeric inspector previews valid changes after a short debounce; Apply is atomic and undoable, Cancel restores the committed transform, Reset draft restores identity. Mouse-driven transform handles, arbitrary rotation and project-wide compositing remain future work.

Acceptance: select a portrait clip; open Transform; choose 1080 x 1920, scale 60, X 80, Y -100. Verify positioning and black borders in preview and exported MP4. Repeat at 150% to verify clipping, on a landscape source and on a cropped clip, then test reset/cancel, save/open, split, undo/redo and source preservation. Compare actual visible content, not just dimensions and signaling. The mpv filter-chain orientation and color behavior still require native Windows qualification.

## Phase 2B.2c: Rotation and flips

The Transform inspector includes Rotate left/right (90 degrees per click) and independent horizontal/vertical flip toggles. Quarter-turn controls also swap the canvas width and height; scale and offsets retain their existing values in output canvas coordinates. Source display rotation is normalized first, followed by source-relative crop, user rotation, horizontal and vertical flips, scale, clipping and padding. The shared planner rejects non-cardinal angles and preserves the existing limited-range HLG transform contract. Orientation fields are optional in version 1 projects and default to zero rotation and no flips. Apply, Cancel, Reset, split and undo/redo use the same transform transaction. No arbitrary-angle rotation or mouse-driven rotation handles yet.

Acceptance: rotate a portrait clip once in each direction, verify the canvas swaps, repeat four quarter turns, toggle each flip on and off, combine crop with rotation and flip using an asymmetric scene, and compare the actual preview against the exported MP4. Test reset, cancel, save/open and split. Native mpv visual equivalence remains a separate gate.

The root run.bat builds and launches the Windows editor from the repository directory. Build failures stop launch and leave a readable error; existing media dependencies are not installed automatically.

## Phase 2B.2d: Transformation equivalence

Qualification is split into independent gates:

1. Automated FFmpeg regression: an asymmetric 10-bit HLG luminance fixture is encoded, remuxed with cardinal display rotations, and processed by the shared geometry planner. Compare unencoded frames from explicit preview-style normalization and FFmpeg autorotation byte-for-byte, verify expected output dimensions, compare actual decoded HEVC export luma with the unencoded reference (mean absolute error at most 8 ten-bit code values), and verify black padding is limited-range code 64. The fixture is synthetic and grayscale; these are not measurements of chroma fidelity or native mpv rendering.
2. Interactive Windows test: `qualify.bat` runs the automated FFmpeg test and `TestNativePreviewEquivalence` with `PIXELCUT_QUALIFY_PREVIEW=1`. The latter uses installed mpv's gpu-next output, the production crop script and the same SDR target settings as the editor. For each of four source orientations, it compares native screenshots of crop-only, rotated/mirrored crop, and scaled/padded crop against screenshots of their corresponding HEVC exports. It requires equal dimensions, global RGB mean absolute error at most 8 on an 8-bit code-value scale, and worst of sixteen spatial blocks at most 18. These are initial engineering acceptance thresholds, not perceptual standards. The script waits for preview readiness and screenshot capture, times out on failure, and uses only temporary synthetic media. It does not require real personal footage. The normal Windows CI job compiles the native test but skips the GPU/display portion without the opt-in environment variable.
3. Manual integration check: on TITAN, use real Pixel 10 footage in the embedded editor, apply asymmetric crop and transforms, pause and scrub, compare against the exported MP4 in the same mpv SDR target, then check cancel/reset/undo and reopening. Confirm orientation, framing, color appearance and responsiveness. The native screenshot gate uses standalone gpu-next windows rather than the embedded child HWND and is not a measurement of monitor HDR output. Neither screenshots nor these grayscale fixtures certify full chroma fidelity, arbitrary HDR formats, or Windows Media Player behavior.

A failure blocks claiming preview/export equivalence. Record exact mpv and FFmpeg versions and failing case; do not relax thresholds merely to make a test pass. The local FFmpeg reference experiment independently checked all eight orientation/filter combinations and limited-range padding. Full native Windows acceptance remains pending.

The first TITAN native run passed ten of twelve cases; crop-only at source rotations 0 and 180 failed. Crop-only previously used mpv's video-output crop property, unlike the passing combined transform cases. Committed crops now use the same lavfi filter planner as the export and combined transforms. ## Phase 2B.3a: Timeline thumbnails

The video lane shows sampled source frames within the clip's current source in/out range. Tile width follows source aspect ratio within 24–96 pixels; samples are quantized by zoom to reduce regeneration. Visible demand is limited to 96 queued tiles, processed by one background FFmpeg worker with an eight-second per-frame timeout, two decode threads and a 256-entry in-memory LRU cache. Failed frames leave the colored clip visible; later timeline redraws may retry after 30 seconds. Shutdown cancels the worker. Cache entries are source-oriented, not cropped/composited, and do not persist across application restarts. Source media is assumed immutable while open. The thumbnail path uses FFmpeg zscale/tonemap to generate approximate SDR BGRA frames, independently of the qualified preview and export pipeline. Native GDI drawing uses top-down 32-bit bitmaps and clips tiles to the visible clip bounds; the playhead and selected edges remain above them.

Acceptance: import portrait and landscape recordings, add clips, wait for thumbnail generation, trim/split, zoom, scroll and move clips. Verify the sample content follows the source interval, no drawing extends past clip boundaries, playback and editing remain responsive and closing the app terminates thumbnail generation. Missing FFmpeg filters or unreadable files should not prevent editing. Automated tests cover tile planning and FFmpeg bitmap output; native drawing and performance need Windows acceptance. Phase 2B.2d native requalification remains outstanding until all twelve cases pass on TITAN.

## Phase 2B.3b: Linked audio waveforms

The A1 linked lane draws actual decoded peak amplitudes rather than a synthetic waveform. FFmpeg decodes the first audio stream into streaming 8 kHz stereo PCM, with aresample first_pts=0 to align initial audio delay to the normalized input timeline. The analyzer retains the maximum absolute channel sample per bin without summing stereo channels. A bounded range-maximum tree supports zoom-dependent aggregation without re-decoding; minimum bin size is 10 ms, and longer sources use coarser bins to cap the summary at 65,536 bins. Rendering maps visible timeline columns to the clip source in/out interval. A single independent audio worker processes up to 32 visible asset requests with a 90-second timeout and a 32-entry memory-only LRU cache; shutdown cancels both thumbnail and waveform workers. Assets over eight hours are not analyzed. Failed analysis leaves a usable linked audio lane and can retry on later redraw after one minute. Source media is not modified. Waveforms are approximate visual aids, not sample-accurate metering. Multichannel input is downmixed to stereo by FFmpeg; source timestamp offsets beyond ordinary normalized container timing are not yet qualified.

Acceptance: import footage with audible speech/music, silence, and no audio; verify real peaks, silent baseline and absent lane content respectively. Trim and split a clip, move it, scroll and zoom; verify peaks track the source interval and the playhead remains above them. Check playback responsiveness and shutdown while decoding. Automated tests cover peak extraction, stereo phase cancellation avoidance, memory bounds, source interval mapping and delayed-audio fixture decoding. Native Win32 rendering and timing on real footage remain pending.

### Thumbnail resize stability

Thumbnail sample keys now use source-anchored power-of-two time levels rather than a grid anchored to the trim edge. At the same sampling level, right trims retain existing sample keys; left trims change only a newly clipped boundary sample. Zoom and auto-fit size changes within a level retain keys; adjacent levels share grid samples. Cached nearby frames from the same asset and source interval are temporary fallbacks while exact samples are pending. The worker pauses queued extraction during a clip drag (one already-running decode may finish), and changes in visible demand are debounced by 180 ms. Unchanged repaint requests do not reset the debounce. Thumbnails are approximate navigation aids, so temporary fallback frames may differ from the final sample. The cache remains bounded and memory-only. Acceptance: trim both ends repeatedly, resize the editor in fit mode and zoom, observing thumbnail continuity and no new extraction starts during a sustained drag.

## Automatic session recovery and stable playhead

The desktop editor maintains two checksummed, sequence-numbered recovery snapshots in `%LOCALAPPDATA%\PixelCut`, separate from manual Save As files. Each committed project mutation checkpoints via refresh; Save As checkpoints the clean state and path. Timeline view changes checkpoint at most once per second, excluding active drag/scrub transactions. A successful snapshot is synced before replacement of the inactive slot; the other slot remains valid if replacement fails. A process-held exclusive lock prevents multiple instances from writing the same session. Startup selects the latest valid snapshot, retaining references to missing sources. When neither slot is valid, recovery is disabled rather than overwriting evidence. The title/status indicates failure, and closing with unavailable recovery requires confirmation. Normal close also retains the last session. Only committed edits are restored; undo/redo history, pending jobs and unapplied drafts are not serialized. Manual project files are never overwritten by recovery.

Clip mouse-down records a click timestamp without moving the playhead; a true trim or move keeps the prior absolute timeline marker, clamped only if the project becomes shorter than that position. A click without a drag still seeks. On a committed drag, auto-fit is converted to its current explicit zoom when within the supported zoom range, so resizing the last clip does not move the marker on screen through automatic rescaling; Fit restores auto-fit. Test forced termination after importing, trimming, applying transforms and moving the playhead; relaunch, verify assets, timeline, marker and view. Verify missing media, corrupted newest snapshot, explicit New/Open, clean close, concurrent launch and failed recovery directory access. Test left/right trim and move with the marker elsewhere, including shortening the last clip past the marker. A process crash can lose the most recent view change within the checkpoint interval; committed edits are saved synchronously. Physical forced-close and UI acceptance remain pending.

## Phase 2B.3c: Magnetic snapping and media-bin removal

Snapping is enabled by default. Clip moves consider both edges; left/right trims consider the manipulated edge only. Targets are the timeline origin, playhead and other clip boundaries on V1. The nearest valid alignment within eight timeline pixels (capped at two seconds) wins; ties use the earlier target. Candidate edits still pass the existing source-bound and overlap validation. A cyan guide marks the snapped boundary. Toggle snapping with the Snap toolbar button or N when the timeline has focus; hold Shift during a drag to bypass it. The toggle is session-local and defaults to enabled on restart. Snapping does not ripple neighboring clips or move the playhead. Frame-accurate snapping and hysteresis remain future work.

Delete in the focused media bin, or the Remove asset button, removes the selected asset reference from the project. Unused assets are removed immediately. Referenced assets require explicit confirmation to remove all of their associated clips, without ripple or disk deletion. Removal is one undoable project mutation and is included in automatic recovery. Delete in the timeline still removes only the selected clip. Text editing retains normal Delete behavior.

Acceptance: move a clip toward a neighboring boundary from both sides, trim to the playhead, observe the guide, bypass with Shift, disable snapping, and attempt an invalid overlap. Remove an unused asset with Delete; remove a referenced asset and cancel the confirmation, then confirm and undo. Verify source media remains untouched and the updated project survives restart. Automated model tests cover exact alignments, overlap rejection, bypass, nonmutating removal and shortcut routing. Native interaction testing remains required.

### Media-bin source identity

Import checks the normalized absolute path and filesystem identity (os.SameFile) before inspecting a source, and the project AddAsset operation repeats the check before insertion. A duplicate selects the existing media-bin entry without creating an undo step. Different files with identical names or bytes are distinct. On opening or restoring an older project, compatible duplicate assets are consolidated to the first entry and every clip asset ID is remapped; clip IDs, timing and edits are preserved. Conflicting metadata is not merged automatically. Missing files are matched by identical cleaned paths only. Saved project files are not rewritten by the migration; recovery snapshots retain the migrated state. Multiple clips may still reference the same asset.

## Phase 2B.3d: Explorer drag-and-drop import

The Windows editor accepts native Explorer file drops through WM_DROPFILES on the media bin, timeline and main window. Unicode paths are read with DragQueryFileW, and the shell drop handle is always released. The Import video dialog also supports multiple selections. Both entry points share one background import pipeline, limited to 64 files per batch, with a 20-second FFprobe timeout per inspected file. Existing assets and repeated paths within a batch are skipped through the existing filesystem identity check. Regular files are inspected against the current supported HLG contract; directories and unsupported files are reported, while valid files in the same batch are retained. A successful batch is a single undoable project mutation and is checkpointed on completion. No files are copied, moved or deleted. All drops import into the media bin, including drops over the timeline; automatic timeline placement and internal media-bin-to-timeline dragging are future work. Dropping on the separate mpv child window is not supported. Drops during an active edit or media operation are rejected. Native Explorer delivery and dialog selection require physical Windows acceptance; ordinary unit tests cover batch behavior and selection parsing.

Acceptance: drag one video, multiple videos, repeated paths, an invalid file mixed with a valid recording, and a folder from Explorer onto the media bin and timeline. Check the import summary, source preservation, selection, undo/redo and session recovery. Repeat via the multi-select file dialog. Use a normal non-elevated PixelCut process so Windows integrity-level restrictions do not block Explorer drops.

## Phase 2B.3e.3: Ripple editing

Regular Delete leaves a gap. Shift+Delete or Ripple delete removes selected clips and subtracts their cumulative durations from later clips, preserving unrelated existing gaps. Remove gap (G) closes the bounded empty interval containing the playhead, including a leading gap; it rejects an occupied position or a trailing unbounded interval. Ripple: on/off (R) enables optional ripple edge trimming, off by default on restart. Both edge trims keep the edited clip's timeline start fixed; changing source in/out shifts every subsequent clip by the duration change, preserving their spacing. In ripple left trim the pointer controls the source in-point rather than moving the clip start; a cyan cut-position guide marks the original coordinate. Ripple trim snaps to the stationary playhead only (Shift after mouse-down bypasses snapping), not to boundaries that are themselves moving. Ordinary move/trim snapping is unchanged with ripple off. Group movement is not ripple movement. The live drag renders downstream clip positions; edits are validated and committed as one undo operation with session recovery. The absolute marker is preserved except when clamped to the new project end. No source media is modified. No-op ripple trims are not committed. The current scope is V1 with linked audio, not independent tracks.

Acceptance: ripple-delete one and several nonadjacent clips, preserve unrelated gaps, remove leading/interior gaps, reject occupied and trailing positions, enable ripple trimming and shorten/extend both edges, inspect downstream motion, undo/redo and recover after restart. Verify ordinary Delete and media-bin Delete remain unchanged. Automated model tests cover cumulative shifts, gap detection, source limits, snapping and original-project immutability. Native input testing remains pending.

## Phase 2B.3e.6: Precision playback and editing

Comma/period and the Frame buttons seek to the previous/next decoded frame timestamp inside the selected clip; they pause playback and do not assume a constant frame rate. The original 0.1-second Left/Right shortcuts remain unchanged. Ctrl+Left/Right jumps to the previous/next clip start or end in chronological order (including across gaps); the last boundary remains at project end without starting a new preview. I/O sets the selected source In/Out boundary at the nearest valid decoded timestamp to the playhead, using ordinary or ripple trim semantics according to the existing ripple toggle. Out is exclusive; the source duration is also a legal exclusive endpoint. B or Frames: on/off enables source-frame trim snapping, independently of magnetic snapping; the source frame grid takes priority for trim edges while enabled, with Shift during drag bypassing it. Frame snapping is not a fixed-FPS timeline grid and does not quantize group moves or asset placement. Frame stepping remains inside the selected clip; edit-boundary jumps navigate between clips. A four-source in-memory cache indexes decoded FFprobe best-effort presentation timestamps normalized to format start time. The first operation on a source runs a background index job (90-second limit and one million decoded frames); trim-drag indexing requires retry after completion. Duplicate timestamps, missing timestamps, and failed probes are rejected rather than guessed. Cache entries are invalidated when file size or modification time changes. The timeline ruler uses 1/2/5 decimal subdivisions, with six-digit fractional-second marker display. The Speed button cycles 0.25x, 0.5x, 1x, 1.5x, and 2x; brackets change speed one step; speed is sent to mpv over IPC, affects preview only, and defaults to 1x on restart. Source-frame snapping defaults off; no frame index is persisted. Existing project edits and marker positions remain recoverable. Decoded timestamp precision is one microsecond, not SMPTE drop-frame timecode. Native mpv seek/display equivalence on actual Pixel VFR footage, unusual source timestamp offsets and transformed-preview stepping require runtime acceptance.

Acceptance: step forward and backward across irregular frame intervals within a trimmed clip, verify displayed frame and marker, jump clip boundaries/gaps, set I/O with and without ripple, trim with source-frame snapping and Shift bypass, change speed during playing and paused states, and confirm exports preserve original timing. Verify source index failure does not change the project. Tests cover decoded VFR probe, timestamp parsing, bounds, edit navigation, ruler spacing, speed request preservation and keyboard routing.

## Phase 2B.4.1: Project lifecycle

Save (Ctrl+S) updates the active .pixelcut.json file; for an untitled project it opens Save As. Save As (Ctrl+Shift+S) creates a new file and deliberately refuses to overwrite an existing file. New, Open, Recent and Close project (Ctrl+W) prompt to save, discard or cancel if there are unsaved committed edits. Close returns to an untitled empty workspace; closing the application still checkpoints the last session as before. The window title displays the project filename without the extension and an asterisk when the current project differs from the saved fingerprint. Undoing back to the saved state clears the marker. Recovery errors remain visible in the title.

Manual writes validate and serialize to a bounded temporary file in the destination directory, sync it, then publish via hard link for Save As or rename replacement for Save. Save checks the previously loaded/saved SHA-256 revision before staging and immediately before replacement, refuses missing, changed or non-regular destinations, and does not adopt an unknown dirty legacy recovery revision. These checks detect ordinary external changes; they are not an exclusive cross-process transaction or a guarantee against an external writer racing the final rename. Save As is the safe fallback. Session snapshots carry the saved revision and semantic fingerprint; if a crash occurred after saving but before checkpointing, identical on-disk content is reconciled at startup. If a recovered project conflicts with a newer disk version, it remains dirty and normal Save refuses the stale revision. Old session files remain readable. Recent lists up to 12 successfully saved/opened paths, newest first, persisted in recent.json in local application data. Missing recent entries are marked, opening one reports the error without replacing the workspace. Clear recent projects removes only the list, never files. Recent storage errors are nonfatal. This phase does not yet preserve independent recovery history across project switches, or create versioned backups. Source files are unchanged.

Acceptance: save an untitled project, edit and save repeatedly to the same file, verify Save As cannot replace an existing file, undo to the saved state, test all three switch prompt outcomes including cancelled Save As, open from Recent after restart, clear the list, close the project, and externally modify/delete a saved file before attempting Save. Test dirty recovery from a previous build and a save/checkpoint interruption. Native Windows dialog and filesystem replacement behavior require runtime acceptance.

## Phase 2B.4.4: Persistent media cache

The desktop reuses local disk cache entries for source thumbnails, decoded audio peak summaries, decoded frame timestamps and import metadata. The cache resides in the dedicated media-cache-v1 directory below the existing local PixelCut cache folder (normally %LOCALAPPDATA%\\PixelCut on Windows). Entries are shared across projects and restarts, independent of project asset IDs. Keys include format version, normalized absolute source path, source size and modification time, executable path/size/mtime, operation kind and parameters (thumbnail timestamp/size or waveform duration). Source stamps are checked on refresh and approximately every two seconds; changed or missing media no longer uses the old thumbnail/waveform memory keys. File content is not fully hashed; changes that preserve both size and modification time are not guaranteed to be detected. Moving a source path generates a new key. Cache hits still require access to the source and relevant media tool. Export and render inspection remain uncached. Import metadata excludes format/stream tags; source geometry side data is retained for validation.

The Cache toolbar menu shows disk usage and entry count, offers persistent limits of 256 MiB, 1 GiB (default) and 4 GiB, and clears disposable cache data after confirmation. The store uses SHA-256 key and payload verification, bounded entry sizes, staged writes, least-recently-used eviction, and a 32,768-entry ceiling. Old invalidated entries remain until eviction or clear; interrupted staging files are cleaned on startup. Clear stops thumbnail/waveform workers before deleting tracked cache entries, clears frame indexes in memory and restarts workers. Visible media then regenerates on demand. Project files, original media and recovery snapshots are not deleted. Unavailable cache storage falls back to memory/decoding; cache write failures do not fail edits. Local cache data includes derived media and should be treated as private. No network service is used. Cache configuration is independent of future application preferences. Tests cover restart reuse, source/tool/parameter identity, corruption, bounds/eviction, clear safety, binary formats, real HLG media integration and probe avoidance. Windows interactive acceptance and real-world speed measurements remain outstanding.

## Phase 2B.4.3: Missing media and relinking

Opening or restoring a project preserves all asset and clip references even when source files are unavailable. The media bin prefixes unavailable files with [OFFLINE], the video and linked audio lanes display offline placeholders, and the Relink toolbar button shows the number of offline assets. Availability refreshes on project refresh and approximately every two seconds; reappearing files at their original path are recognized automatically. Offline clips remain editable through non-media operations such as move, trim, split, copy and delete. Preview, visual crop/transform, frame indexing and export require accessible media. The project does not rewrite or remove offline references automatically.

Select an offline media-bin asset and choose Relink selected offline asset, or use the asset/clip context menu. Select the intended file. The editor freshly probes the candidate (not cached metadata), validates the supported HLG contract, cardinal rotation/display dimensions, exact stored duration, audio presence and known color range, and validates the entire resulting project. For older assets without a stored range, a valid candidate range is adopted only if all edits remain valid. The existing project schema records displayed orientation dimensions rather than original encoded rotation or complete content fingerprints; matching metadata is not proof of identical footage. Every relink requires explicit confirmation. Replace source is a separate deliberate action, allows compatible different-duration footage only when every existing source interval and transform remains valid, and preserves the asset ID and all clip IDs/properties. Both modes reject a file already assigned to another asset, including filesystem aliases. No media files are moved, copied or deleted.

Search folder for offline assets uses a native directory picker and scans only the chosen folder (nonrecursive). It matches case-insensitive basenames, skips ambiguous matches and duplicate missing basenames, probes up to 64 candidates in a batch and reports unresolved assets. Directory scans are bounded at 100,000 entries; each probe has a 20-second timeout and the batch has a three-minute deadline. No changes are committed until the user confirms the compatible candidates. Candidate size/mtime is checked before/after inspection and at confirmation; if an accepted candidate changes or the original source reappears, the whole proposed batch is rejected. Each successful batch is one undoable, checkpointed edit. Save persists the updated references. Disk and memory cache keys follow the new source path/stamp; old cache entries are left for eviction. A clipboard referencing changed asset metadata must be recopied before paste. Metadata-only edits can remain possible offline, but precise source-frame operations require a readable source. No content hashing or automatic replacement on filename match is performed. Existing paths that become readable again are checked for availability, not automatically re-probed for content equivalence. Physical Windows file/folder dialog and preview acceptance remain pending.

Acceptance: save a multi-clip project, move source files while closed, reopen and verify offline placeholders with unchanged clip edits, relink a moved file, reject incompatible duration/geometry/range/audio, explicitly replace with compatible footage, batch-search a folder containing correct, mismatched and missing names, cancel the confirmation, undo/redo a batch, save/reopen, and restore a previously offline file at its original path. Verify source files and recovery data remain untouched and the thumbnail/waveform cache regenerates for newly linked paths.

## Phase 2B.4.5: Application preferences and gap playback

The Settings toolbar button (Ctrl+, outside text fields) opens native checked options for magnetic snapping, ripple trimming, source-frame trim snapping, startup paused-preview restoration, SDR/HDR preview output, speed, recovery view checkpoint interval and executable paths. Editing toggles and preview speed persist immediately, whether changed by the menu, existing toolbar buttons or shortcuts. Defaults preserve existing behavior: magnetic snapping on; ripple/frame snapping off; SDR preview; normal speed; restore paused preview on startup; one-second view checkpoint. Preferences use a separate versioned, strictly decoded JSON file in the local PixelCut folder, with staged/synced replacement. Missing preferences use defaults; corrupt or unsupported preferences use defaults and report a warning. Storage failures leave runtime changes active but report that preferences were not saved. Reset restores these settings without deleting projects, media caches or recovery data. The Cache menu continues to own disk budget settings. The startup option disables reopening the paused preview only, never recovery of edits. Checkpoint intervals (1, 5 or 15 seconds) apply to view changes; committed project edits still checkpoint immediately. HDR preview is experimental, requires a compatible configured display, and does not affect export. FFmpeg, FFprobe and mpv can be selected individually; a background version command checks the selected executable's identity before adoption, not its complete feature support. Tool changes stop preview, restart media workers and clear memory frame indexes; disk keys include tool identity. Automatic tool discovery restores the previous PATH/installation lookup. Cache location, preview quality presets, independent recovery histories and backup retention are deferred.

Play/Space resolves playback against the absolute timeline marker, not the selected clip. If the marker lies within a clip, playback starts or resumes there. In leading or interior empty space, it jumps to the earliest subsequent clip start in timeline order and begins playback. At or beyond the final end, Play does not wrap or rewind. Seeking exactly to project end preserves the end marker and stops preview. Offline clips are not silently skipped; they still report missing media. This change does not yet implement real-time black/silent gap playback or continuous transitions at end of a clip; Play at a completed clip can advance to the next one. The source-interval preview architecture otherwise remains unchanged.
